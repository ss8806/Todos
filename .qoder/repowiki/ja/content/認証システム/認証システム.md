## 導入
本認証システムはJWT（JSON Web Token）ベースの認証を実装しており、以下の機能を提供します：
- ユーザー登録：メールアドレスとパスワードによる新規登録
- ログイン：OAuth2のパスワードフローによるアクセストークン取得
- ログアウト：クライアント側でのトークン破棄（サーバー側には不要）
- パスワードリセット：メール経由のリセットフロー
- 認証ミドルウェア：保護されたエンドポイントへのアクセス制御

本ドキュメントでは、認証エンドポイントのAPI仕様、リクエスト/レスポンススキーマ、JWTトークンの生成と検証プロセス、パスワードハッシュ化、トークンの有効期限管理、認証ミドルウェアの動作原理について詳しく解説します。

## プロジェクト構造
バックエンドはFastAPIフレームワークを用いており、認証に関連する主なモジュールは以下の通りです：
- APIルーター：/api/v1/auth 以下に認証エンドポイントを配置
- セキュリティ：JWTの生成・検証、パスワードハッシュ化

- モデル：SQLModelによるデータ定義
- 設定：JWTアルゴリズム、シークレットキー、有効期限、レート制限など
- ミドルウェア：エラーハンドリング（バリデーション、HTTP例外、レート制限）

## アーキテクチャ概要

- APIエンドポイントはFastAPIのルーターを通じて提供
- 認証ミドルウェア（OAuth2PasswordBearer）により、保護されたエンドポイントにアクセスする前にトークン検証が実施
- JWTの生成・検証はセキュリティモジュールで処理
- DB接続は非同期SQLAlchemyセッションで管理
- エラーハンドリングは共通ミドルウェアで一元化

## 詳細コンポーネント分析

### API仕様とスキーマ
- 認証エンドポイント
  - POST /api/v1/auth/register
    - 要求スキーマ：UserCreate（email, password）
    - 応答スキーマ：UserRead（id, email）
    - 状態コード：201（成功）、400（メール重複）
  - POST /api/v1/auth/token
    - 要求スキーマ：OAuth2パスワードフォーム（username, password）
    - 応答スキーマ：Token（access_token, token_type）
    - 状態コード：200（成功）、401（認証失敗）
  - POST /api/v1/auth/forgot-password
    - 要求スキーマ：ForgotPasswordRequest（email）
    - 応答スキーマ：メッセージ（常に200）
  - POST /api/v1/auth/reset-password
    - 要求スキーマ：ResetPasswordRequest（token, new_password）
    - 応答スキーマ：メッセージ（200）
- 共通スキーマ
  - Token：access_token, token_type
  - UserCreate/UserRead：email（unique, index）、password（登録時のみ）、id（登録後のみ）

### JWTトークンの生成と検証プロセス
- 生成
  - トークンペイロードにsub（ユーザーID）を設定
  - exp（有効期限）を現在時刻＋設定値（分）として追加
  - HS256アルゴリズムで署名されたJWTを生成
- 検証
  - 例外（JWTError）を補足し、無効なトークンはNoneを返す
  - FastAPIのOAuth2PasswordBearerにより、Authorization: Bearer トークンが要求される
- 有効期限管理
  - 設定：ACCESS_TOKEN_EXPIRE_MINUTES（分）
  - トークンペイロードにexpを含めるため、期限切れの場合は検証に失敗

```mermaid

Start(["JWT生成開始"]) --> Prepare["ペイロード準備<br/>sub, exp設定"]
Prepare --> Encode["JWT署名<br/>HS256"]
Encode --> Token["JWT文字列"]
DecodeStart(["JWT検証開始"]) --> Decode["署名検証<br/>HS256"]
Decode --> ExpCheck{"expチェック"}
ExpCheck --> |有効| Payload["ペイロード取得"]
ExpCheck --> |無効/例外| Fail["検証失敗None"]
```

### 認証ミドルウェアの動作原理
- OAuth2PasswordBearer
  - tokenUrlを"/api/v1/auth/token"として設定
  - 保護されたエンドポイントにアクセスする際、Authorization: Bearer トークンが必要

  - トークンをデコードし、subからユーザーIDを取得
  - UUID形式の検証、DBからユーザーを取得、存在しない場合は401
  - トークンが無効または期限切れの場合、401

### パスワードリセットフロー
- トークン作成
  - 既存の未使用トークンを無効化
  - 新しいトークン（生のトークン＋ハッシュ）を作成
- 送信
  - メール送信（宛先：ユーザーのメールアドレス）
- 検証
  - 生のトークンをハッシュ化してDBから取得
  - 有効期限内かつ未使用か確認
- 更新
  - 新しいパスワードをハッシュ化して保存
  - トークンを「使用済み」にマーク

## トラブルシューティングガイド
- 認証エラー（401 Unauthorized）
  - トークン形式が不正（Bearer指定漏れ、無効なJWT）
  - トークンのsubがUUID形式でない
  - DBに該当ユーザーが存在しない
- トークン検証失敗
  - 期限切れ（exp超過）
  - 署名アルゴリズム/シークレットキー不一致
- レート制限超過（429 Too Many Requests）
  - 認証系エンドポイントの呼び出し回数が設定値を超えた場合
- その他のエラー
  - 400/404/422などのHTTP例外は共通エラーハンドラーにより整形されて返却
