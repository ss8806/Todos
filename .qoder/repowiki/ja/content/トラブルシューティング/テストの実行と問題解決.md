## はじめに
本ガイドでは、ユニットテスト（Pytest）とE2Eテスト（Playwright）の実行方法、テスト失敗時の問題解決手順、テスト環境のセットアップ、テストデータ管理方法について詳しく解説します。また、環境変数の不一致、データベースの状態、ネットワークエラーなどの一般的な失敗原因とその対処法、テストのデバッグ手法、CI/CDパイプラインでのテスト実行についても網羅的に説明します。

**更新** E2Eテストのパフォーマンスが大幅に向上しました。Playwrightのexpectタイムアウトが5秒から10秒へ増加し、ユーザーFixtureシステムのリトライ回数が8回から3回へ削減され、最大待機時間が128秒から9秒へ短縮されました。認証テストとTodoナビゲーションテストの不要な待機時間も削除され、テストの実行速度と安定性が向上しました。

### Python的アサーションスタイルの採用

**更新** テストコードにおけるPython的なアサーションスタイルの導入

本プロジェクトでは、Pytestのユニットテストにおいて、よりPython的で直感的なアサーションスタイルを採用しています。これにより、テストの可読性と保守性が大幅に向上しています。

#### 主なアサーションスタイル

1. **真偽値の直接評価**
   ```python
   # 例：Todo作成後の完了状態確認
   assert data["is_completed"]  # Trueの場合に成功
   ```

2. **否定値の評価**
   ```python
   # 例：新規Todoの初期状態確認
   assert not data["is_completed"]  # Falseの場合に成功
   ```

3. **組み合わせ使用**
   ```python
   # 例：削除後の存在確認
   assert not any(todo["id"] == todo_id for todo in todos)
   ```

#### 実装例

- **Todo作成テスト**：`assert not data["is_completed"]`（新規作成時は完了していないことを確認）
- **Todo更新テスト**：`assert data["is_completed"]`（完了状態に更新されることを確認）
- **Todo削除テスト**：`assert not any(...)`（削除されたTodoが存在しないことを確認）

## 結論
本プロジェクトでは、Pytestによるバックエンドユニットテスト、Jestによるフロントエンドユニットテスト、PlaywrightによるフロントエンドE2Eテストを、PostgreSQLサービスを活用して安定的に実行しています。環境変数、DB状態、ネットワーク、レートリミットといった一般的な失敗要因に対して、設定ファイルとCIジョブで対策を施しています。テストのデバッグやCIでの継続的実行を円滑にするために、トレース/スクリーンショット/ビデオの収集、再試行、タイムアウト設定が適切に行われています。

**更新** E2Eテストのパフォーマンスが大幅に向上しました。Playwrightのexpectタイムアウトが5秒から10秒へ増加し、ユーザーFixtureシステムのリトライ回数が8回から3回へ削減され、最大待機時間が128秒から9秒へ短縮されました。認証テストとTodoナビゲーションテストの不要な待機時間も削除され、テストの実行速度と安定性が向上しました。これにより、テストの実行時間が短縮され、レートリミットエラーの発生確率が低下し、全体的なテスト品質が向上しています。

  - `assert not data.get("error")`：エラーフラグの確認

- **可読性の向上**
  - `assert not data["is_completed"]`の方が`assert data["is_completed"] == False`よりも明確

### 5. Playwright設定の改善点

**更新** E2Eテストのパフォーマンス向上に関する設定改善

- **expectタイムアウトの増加**
  - `expect.timeout: 10000`（前は5000）
  - テストの安定性を向上させ、一時的な遅延に強い耐性を持つ

- **ユーザーFixtureのリトライ回数の削減**
  - `maxRetries: 3`（前は8）
  - 待機時間の短縮と、レートリミット対策の強化

- **最大待機時間の短縮**
  - `waitTime: Math.min(attempt * 1000, 3000)`（最大3秒）
  - 429エラー時のリトライを効率的に制御

- **不要な待機時間の削除**
  - 認証テストとTodoナビゲーションテストから不要な`waitForURL`呼び出しを削除
  - テストの実行速度を大幅に向上

- **恒常的な`reuseExistingServer: true`の利点**
  - テスト間でのサーバー再起動を省略し、起動オーバーヘッドを削減
  - テストの信頼性を向上させ、一貫した実行環境を維持
  - CI/CDパイプラインでのテスト実行時間を短縮
